# HTTPS-record discovery completion design

Bound source: `400a900e9051855d1f310a6dda603d057f700937`. The complete 461-line discovery parent was read. Supporting implementation/dependency reads are partial, with exact ranges and hashes in JSON. Reviewed implementation bytes also match `0340818c`; the separate import-only working change is assessed in its own addendum. Existing A228 remains the finding; this report does not create a duplicate or allege a production defect.

A test-local completion notification is sufficient under the current source and an explicit current-thread runtime. `from_fn` boxes the supplied future and `lookup` returns its awaited result directly. After that Ready result, the discovery task synchronously summarizes records or failure, computes TTL, calls `LookupOwner::complete`, inserts Ready state, then attempts `watch::Sender::send`. There is no await between result and insertion. The tracing wrappers delegate one inner poll directly. Tokio's current-thread scheduler finishes that task poll before polling the waiting test again; notification wakes rather than preempting the task. Default test flavor is currently current_thread, but make it explicit because the contract depends on it.

Keep the boundaries separate. DNS `queries()` records arrival before a delayed reply is spawned. The custom resolver observes its actual upstream Result; cache completion follows later in the same poll. Production watch publication is attempted after insertion and may fail when all pending receivers have been dropped. Thus a test-local signal does not independently observe successful production watch publication. The private `failed_lookup_is_remembered_as_no_advertisement` companion retains a real receiver through `settle`, then calls the actual discovery consumer and requires `NotAdvertised` rather than `Pending`.

Return a private observed resolver together with a watch receiver and an invocation counter. Inside its original renamed loopback DNS future, await the actual upstream lookup, copy only outcome metadata (success or the actual `HttpsLookupErrorKind`), synchronously `send_replace` that metadata, and immediately return the original Result unchanged. No yield, spawn, blocking executor, result substitution, or additional await is allowed after the signal. Retain the receiver before client acquisition. Await its first completed value under the existing outer 20-second bound; do not hold a watch Ref across another await. Keep any failure/cancellation and fixture cleanup outcomes visible using the established concrete owners.

Use the barrier once before the existing second request in sequential, failed-lookup and enabled-discovery passes. For misdirected HTTP/3, wait after `/learn`; the 421 path marks the alternative broken synchronously before returning its response, so neither later loop iteration needs a readiness sleep. In the delayed sequential pass, replace both the absolute `sleep_until` and 200 ms wait with actual completion. Preserve the 4500 ms DNS delay and original first-response elapsed/protocol assertion; additionally snapshot that the completion value is still absent at that response if claiming pending lookup readiness. The racing pass has no later cache-consumer assertion and must not receive that extra claim. Disabled discovery and proxy routes must never wait for an observer that cannot fire.

For completed-failure caching, require an actual Resolve failure observation before issuing the existing second trusted HTTP/2 request. Snapshot DNS arrivals and actual resolver invocations at completion, require nonzero real DNS traffic and one resolver invocation, then retain the original two-request/protocol/body/record assertions and unchanged counts. This removes the present ambiguity where stable counts can mean one lookup still pending. Counts remain supporting wire evidence, not a separately observed cache entry; the same-poll source contract and the private `NotAdvertised` consumer provide the stronger boundary. A missed publication must fail the finite completion wait, not pass via a sleep. A controlled held-result companion can preserve a real upstream result while preventing its Ready return, prove the original pending-origin behavior, and release it on every exit before finite cleanup.

A multithread test cannot use this notification as an insertion barrier: another worker may resume the waiter between send and insertion. If that runtime is required, keep the direct cache contract in the existing private test module and wait on its actual `PendingLookup` before the `Discovery` consumer. That already supplies a real consumer without a new public API, relocation, or production-only observer seam.
