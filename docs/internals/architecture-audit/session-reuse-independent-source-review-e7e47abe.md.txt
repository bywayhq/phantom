## Confirmed findings

1. A236: spawned tasks lack an owner on exceptional exits. The seven tests
   with peers retain raw server, proxy, or request JoinHandles across fallible
   client setup, sends, body collection, and assertions. Dropping those handles
   detaches pending tasks and removes the ability to observe completed errors.
   This applies to first/second caller tasks as well as server tasks. In the
   independent-client test, the first nested server handle at 201 crosses
   fallible second TLS acceptance at 202. The second nested handle at 203
   crosses the fallible first join at 204. A timeout also drops the enclosing
   future and its raw handles. Resolved Tokio 1.53.1 documents this detachment
   contract explicitly. No permanent leak or production defect was measured.
2. A233: `bounded` at 554–561 replaces the original Tokio `Elapsed` at 560
   with a static contextual string. Context remains, but the typed underlying
   deadline cause is lost. The timeout is one bound around the full test body,
   not separate per-operation five-second budgets.
3. Additional upload helper error loss: `collect_h2_request_body` first polls
   stream data at 488–490. If that is Pending and the subsequent connection
   poll observes clean transport EOF, 492 converts it into `Ok(None)`. The
   resolved fork records BrokenPipe on still-open streams during EOF handling;
   a second stream poll would expose that original error. Instead the helper
   returns its partial buffer as success at 498–499. Existing upload assertions
   or the later follow-up can still fail, so this is not proof of a false-green
   test. It is a concrete discarded stream-error path, currently untested.
4. Readability: the child module at 3 and local support alias at 4 precede
   standard imports. Move imports into standard, external, and local groups,
   then the child module. The rest of the file has a coherent test-first/helper
   reading order; no arbitrary split or new crate is justified by this file.

## Protocol and driver assessment

`Connection::accept` advances the resolved driver's `poll_closed`, and
`poll_closed` drives RecvStream and SendStream progress. The upload collector
therefore must retain its explicit driver polling when body data is Pending.
It releases each received chunk's exact capacity, matching the resolved
flow-control contract. Its allocation is acceptable for this private fixed
payload test; no public unbounded-buffer claim follows.

The cancellation loop at 388–397 drives the connection through `accept`
while waiting for the later request, and polls the original send stream for
reset. Once the later request has been retained, only reset polling remains;
`poll_reset` itself does not drive connection I/O. Current caller order drops
the first body before starting the later request. No evidence here proves
that the intended input violates that ordering, so an arbitrary reordered
peer deadlock is not elevated to a confirmed current-test defect. Keep this
qualification if the fixture is broadened, and continue driving the same
connection if later-before-reset input becomes an intended contract.

The HTTPS relay's four-kind peer-disconnect predicate is documented in shared
TLS support. Its tolerance is specific to fixture teardown. The plaintext
relay propagates all copy errors. This review does not require equalizing
those policies or broadening either predicate without a causal control.

## Smallest complete remedy and verification

Use the existing concrete connection owner for every outer server, relay,
and caller task. Keep ownership alive outside the timed operation so expiry
can still perform finite explicit shutdown and join. Preserve a primary
request/deadline cause alongside every observed cleanup cause. Drop should
remain an abort safeguard; it cannot replace a join or prove destruction.
Completed task errors and unexpected JoinErrors must remain visible.

Remove the two nested server spawns in the independent-client fixture.
Concurrently drive canonical `serve_requests(first, 1)` and an async second
TLS accept followed by canonical `serve_requests(second, 1)` within the one
owned outer server task. That preserves first-server progress during the
second accept and gives the parent direct ownership of both future lifetimes.
It avoids claiming that merely joining an aborting parent has reaped detached
children. Do not copy the server logic or stop H2 driving after queuing 204.

For the upload collector, re-poll the same RecvStream after driver closure so
queued DATA, normal stream end, or the original stream error determines the
result. Preserve driver errors. Do not treat transport closure as stream EOF.
Preserve original Elapsed with a small contextual error whose source is the
Elapsed value, rather than fabricating another timeout.

Regression controls should use the actual factories, original task handles,
and driver futures. Include healthy response/body consumption, an explicit
abort and finite join, a fallible setup after acquisition, a Pending accepted
peer followed by owner Drop while the runtime and client stay alive, a
completed typed sibling failure, and a second-accept failure while the first
H2 service is active. Observe original cause identity and socket/driver
closure before backup cleanup. Add an incomplete upload whose first body poll
is Pending and whose actual transport EOF produces the resolved BrokenPipe;
require the original stream error rather than only a later length mismatch.
Run all eight existing tests and new controls on Windows and Linux, plus the
applicable strict compiler, format, MSRV, and integration gates.

No source implementation, formatter, Cargo command, native test, checker,
probe, push, merge, or release was performed by this reviewer. All findings
remain source-confirmed until causal regression controls and remedies are
independently reviewed and executed.
