## CACHE-TEST-READINESS-F1

`address_cache/tests.rs:296-318`, `340-381`, `866-890`.
The first and clear controls open their resolver gate after one yield.
The cross-runtime control sleeps before gate release. These do not prove
that the relevant spawned lookup reached pending selection. A single
resolver call can also result from sequential stored hits, so the count
alone does not prove concurrent sharing or a cross-runtime join.
In the clear control, registration after clear would exercise the wrong
generation and may produce an unrelated assertion failure. This is a
source-confirmed causal-readiness gap, not a measured flake or production
cache failure. Tokio 1.53.1 yield_now documentation explicitly says the
runtime need not poll another task after yielding.

A separate tests-only assignment should replace the scheduling assumption:

1. Concurrent sharing: retain eight pinned lookup_noting_cache futures,
   poll each once while the real resolver gate is closed, require Pending,
   and observe one real recorder invocation before release. After opening,
   complete each bounded future and require exact addresses plus false
   stored provenance. A separate existing stored-entry control stays true.
   This proves every lookup was selected before publication, rather than
   relying on scheduler order or reproducing cache internals.
2. Clear: poll the actual lookup while its resolver is held, observe one
   invocation and real pending registration, then clear. Release the gate,
   retain the old exact answer, require the cache remain empty, and keep
   subsequent fresh-resolution/call-count assertions. Preserve stronger
   existing A4 generation/reservation and ready-publication regressions.
3. Cross-runtime sharing: the first runtime polls its retained lookup
   before it stops being driven. The second runtime polls its own retained
   lookup before signalling explicit readiness to the parent. The parent
   observes that signal and exactly one invocation while the resolver gate
   is still closed, then releases it. Completion must be bounded and retain
   its io::Error cause. Require false stored provenance, exact addresses
   and the final call count. A synchronous ready/result channel may bridge
   the two runtimes; its receive failure is a failure, never readiness.
   Remove the scheduling sleep. Observe the thread completion after its
   result rather than discarding a join. Do not introduce a task framework.

These three existing controls should be strengthened in place. Their
production implementation already has independent stronger controls;
new red production failure must not be invented merely to demonstrate a
readability/readiness repair. Parent owns actual native verification and
will assign a separate lane before any source changes.
