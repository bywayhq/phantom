# Profile catalog costs

Use these measurements to assess catalog growth and the cost of selecting and
constructing profiles. They cover one Windows host and an offline workload.

The workload contains 11 real definitions, including the partial Edge 153
registration. Larger cases add synthetic clones with the same components and
evidence. They add no browser coverage. All original definitions remain equal.

## Method

Generation uses seven sequential Python child processes per case. Its timer
covers declaration parsing, validation and all 15 generated Rust output
strings. Hashing and output writes are outside that timer. `tracemalloc` is
enabled, so these times include its overhead. Python heap and process RSS
figures are medians of the sample peaks.

Build rows contain one fresh, isolated profile-only release build each. Rust
1.99.0 ran with `--offline --locked -j1` and incremental compilation disabled.
Each case has its own target directory. Queue time and the later harness
build are excluded. Filesystem and toolchain caches were warm.

Every runtime process first compares every complete profile and all four
template kinds with their original values, including unavailable-kind
errors. Timing uses seven samples: 100,000 selections or 10,000 constructions
per sample. Construction includes dropping the returned owned value.

Memory workers retain 4,096 profiles and their available Navigation templates.
They take three RSS readings at each baseline, retained and dropped barrier.
The table reports medians of seven workers' phase deltas. It does not measure
individual allocation sizes or allocation counts.

## Interpretation

The largest case increased generated bytes, generation time, build memory
and selection cost. Each selected recipe's construction medians stayed within
the recorded ranges across cloned workloads. Recipe differences and the
changing retained mix prevent attributing memory differences to catalog size.

These results do not justify a database, runtime loader, new crate or cache.
Independently captured versions can have different component diversity and
provenance sizes. No handshake, browser observation or service acceptance was
measured. Focused measurements do not replace native replay or integration CI.

RSS includes static data, stacks and allocator retention. Sampling can miss
peaks or count shared pages twice. After-drop RSS alone proves neither live
object retention nor a leak. Other host processes remained active.

## Retained evidence

The owning lane keeps the scripts, frozen inputs, raw samples, binaries and
logs under `target/transport-profile-campaign/`. Preserve these packets when
removing build outputs. Use a fresh packet: generation and runtime commands
can overwrite existing sample logs. The compile/runtime run wrapper rejects
an existing wrapper receipt.

- Generation: `p5-measurements/generation-summary.json`, SHA-256
  `645de4b0c724a86d3832112f9aa936d547899bbd6f249e29415a26304fce91b7`.
- Build and runtime: `p5-measurements-compiled-v2/compiled-runtime-summary.json`,
  SHA-256
  `529ae9d6e79df3af8270e24d3401febecb3f6b0182f90e00d824c4271ec18559`.

The original 932-file generation packet stayed byte-exact. Build and runtime
use a separately retained snapshot with five copies of the reviewed Rust
test-module repair. Its remaining inputs match. A later HTTP/2 registration
and equivalent slice-iteration repair affect native tests outside these
benchmark inputs. Their original failures remain in separate packets.

The retained `measure.py` supports `prepare`, `generation`, `compile` and
`runtime`. Workloads are `REAL_11`, `SYNTHETIC_ADDED_11`,
`SYNTHETIC_ADDED_128` and `SYNTHETIC_ADDED_1024`. Compile uses sample `0`.
Runtime defaults are seven repeats, 100,000 lookups, 10,000 constructions
and 4,096 retained profiles. The script records tools, sources, workload and
binary hashes and uses the root Cargo lock helper. Reproduce into fresh
packets, preserving the original run and host-specific paths.
